So, regarding my game, I started it from scratch again after I learned more about Godot (see my resume). And needless to say, it has completely changed my mind about game development. It is actually really fun.

The main problems I were struggling with in my previous article was synchronization, excessive OOP, and having to re-invent the wheel every time I wanted a new feature.

The most significant feature I was lacking was animations. Moving a character on screen from one spot to another over the course of 1 second seems simple, right? Well, the way I was going about it, NO! It took me weeks to realize that there is one game engine perfect for me, that has that functionality built in!

Godot

Godot is a free and open-source game engine on multiple platforms. Every component in your game is a 'scene', which is a node in a tree of your game objects. Different scenes have different functionality; for example, in a Mario game, you might see a Player scene, a bunch of Goomba scenes, a bunch of Coin scenes, a MusicManager scene, stuff like that.

Almost all of my qualms were addressed by this engine. The dialogue system I spent days on in my previous prototype took me only about an hour. Adding new features is as simple as dragging in new built-in scenes, that have tons of features for different purposes.

Though, there is one thing I dislike about Godot, and that is its proprietary scripting language- GDScript. It's almost identical to python, with a few tiny syntax adjustments and functionality changes. But what I hate is its type system, or lack thereof.

Grandma- "types" are exactly what they sound like. In code, you have different items you need to manage. Some are numbers, some are pieces of text, some are objects, and so on. Those are the types of those things. In complicated code, you have more complicated types, like a list of texts, a map which maps numbers to lists of functions, and so on. A type system is how the programmer can understand what the types of their variables are, and how they can ensure they don't, for example, add a number to a color (which makes no sense to do).

GDScript Type System

I first learned to code seriously in Java, and so I appreciate strong type systems. They have saved me from countless foot guns. The same can not be said about GDScript. The type system seems kind of clunky; you can't strictly type functions as objects, you can't type 2D arrays, there are no generic types, and the typeof function is actually just returning a list of hard coded primitives; this means you can't compare two scenes by their types. Literally, typeof(something) returns AN INTEGER. Meaning, you can't get the typeof user-defined classes!! It only works on the primitive types, like int, PackedInt32Array, and Dictionary. But not any of the scenes! Why would you EVER need that?!

And also, the way to define a class is really stupid.

Grandma- "classes" are how you describe what an object is made out of. For example, for a Person class, you need to define what properties a "Person" has. It would have a name, an age, a height... and so on.

In GDScript, there are, for some reason, I think two different ways to define a class. You can make a new class that is inside a class, or you can use class_name, which transforms the script itself into a class? When combined with the autoload functionality, I keep messing things up. It is stupidly hard to just have a static function.

I understand that GDScript is a scripting language, and thus, typing is less important. But it seriously helps with my chain of thought. My code can get real messy sometimes because I can't figure out what types I'm dealing with. Yes, this is my fault, but a type system would make it so much easier...!

My next complaint is signals and functions. Functions are in a weird in between state of being first-class objects and being objects with properties. In order to pass a function as a variable or a parameter, you can only use the Callable type. This means you can not type by what parameters are in the function. I don't usually say this, but, Typescript does it well. I really like the syntax: const my_func: (a: int, b: int) => int;. It's so cool.

I guess we're talking about type systems now, and I have to say, I REALLY like how Rust does enums. In my opinion, an enum represents some sort of primitive value that can't be modified, and that represents one entry in some stratified finite set of possible values. In Rust, you can add parameters, have different types, have constructors, a bunch of weird stuff but it's so cool. I wish Java had anything of the sort. But who are we kidding- we need more useless Stream functionality! Right? Right?

But evidently, I digress. The biggest flaw in the type system of Godot, in my opinion, is the restriction on nested types. For example, in Java, you could do int[][] or List<List<Integer>>. But, in Godot, writing Array[Array[int]] causes an error, because you can't have nested types. I have no idea why this is, but if I had to guess, it is probably some hardcoded garbage.

I get that Godot is meant to be beginner-friendly, but then why include complicated functionality that requires more complicated code, if you won't provide code to manage it?

Tweens

Now, this is something about Godot that I love. I mentioned earlier how animating certain things is really difficult when programming it from scratch. In GDScript, you can asynchronously start animations and do tons of things with them. In my game, I use the following tween: 

vn.gd
for i in range(3):
  tween.tween_interval(0.1);
  tween.tween_callback(Utils.setter(vn.heartBlink, 'visible', false));
  tween.tween_interval(0.05);
  tween.tween_callback(vn.sfx_noise.play);
  tween.tween_callback(Utils.setter(vn.heartBlink, 'visible', true));
tween.tween_callback(vn.sfx_battlefall.play);
tween.tween_callback(Utils.setter(vn.heartBlink, 'visible', true));
tween.tween_property(vn.heartBlink, "position", stage.position, 0.3);

Basically, step by step, what this does is:

  1. Wait 0.1 seconds
  2. Make the heart icon invisible
  3. Wait 0.05 seconds
  4. Play a sound, and make the heart icon visible
  5. Repeat all of that two more times
  6. Play a sound
  7. Make the heart icon visible
  8. Smoothly move the heart to the center of the screen over 0.3 seconds

The best part about this, is that code runs instantly. While the animation has started, you can start running more operations. This is called a coroutine. In simple terms, a coroutine is a piece of code that will go off on its own, and no matter how slow it runs, and no matter what it does, the main piece of code will proceed onwards without it. It's like having a secretary go print something for you; you can do other work while you wait.

I had to manually add this feature using threads and stuff in my older Java prototype. In Godot, it's as easy as: 

.gd
func _ready():
  await some_coroutine();
  some_other_function();
  some_coroutine();
  some_other_other_function();

In this code, the function some_other_function will wait for some_coroutine to finish. Then, the next time the coroutine is ran, some_other_other_function will not wait for it. This is so amazing, although I do wish the type system specified whether a function was a coroutine, like in Typescript, with Promise<T>.

I spent so long making a SynchronousQueue system in Java, using a bunch of records and matching to get this same functionality, and it was awful. With Godot, it's easy as pie. This tweening functionality is built off of the asynchronous features of Godot, and my oh my, it has helped so much. The script above with the heart icon is from my game, which is a recreation of the battle start animation from Undertale. I'm using Undertale / Deltarune (UTDR) assets as placeholders right now.
